# 01. MVP 설계

> 상태: 초안(2026-11-22). 서비스 이름은 정하지 않았다. 폴더 이름 `repo-inspect`는 임시다.

## 1. 한 줄 정의

GitHub 저장소 링크를 넣으면, 그 AI 도구(skills, hooks, MCP 서버, 플러그인)를 **설치하기 전에** 어떤 권한을 쓰는지, 스타가 진짜인지, 관리되고 있는지를 근거와 함께 한 화면에 보여 주는 웹 서비스.

## 2. 왜 만드는가

- 요즘 GitHub 트렌딩의 중심은 하네스, skills, MCP 서버, hooks, 역공학 도구다. 이것들은 설치하는 순간 셸 명령 실행, 파일 읽기, API 키 접근이 가능하다.
- 사람들은 스타 수와 README만 보고 `git clone`이나 플러그인으로 바로 설치한다.
- skills, MCP, hooks는 npm·pip 패키지가 아니라서 Dependabot 같은 기존 도구가 보지 않는다.
- 비슷한 도구는 흩어져 있다(아래 표). 이 서비스는 이것들의 강점을 한 화면에 모으고, 빈칸을 메운다.

| 이미 있는 것 | 강점 | 이 서비스가 메우는 빈칸 |
|---|---|---|
| mcp-scan | MCP 도구 설명 오염 검사, 설명 해시 비교 | 메타데이터만 보고, 내 컴퓨터에 설치된 것만 검사 → 웹에서 설치 전에, 코드까지 |
| skill-scanner, skill-sentry 등 | skills, hooks 정적 검사, 줄 번호 근거 | 검사기를 먼저 설치해야 함, 영어, CLI → 웹, 한국어, 설치 불필요 |
| StarScout | 가짜 스타 판별 기준(연구 검증) | 연구용이라 무거움 → 표본만 가볍게 |
| OpenSSF Scorecard, Socket | 관리 상태 점수, 공개 API | AI 도구 고유 위험(권한, 인젝션)은 안 봄 → 권한 명세서와 합침 |
| 깃밥 | 트렌딩 한국어 해설, 4관문 검증 | 점수 계산식 비공개, 권한 표시와 가짜 스타 검사 없음 → 근거 공개 |

## 3. MVP 범위

### 넣는 것

- F1. 저장소 링크를 넣으면 분석 작업이 만들어지고, 진행 상황이 실시간(SSE)으로 보인다.
- F2. 결과 페이지는 공유 가능한 고정 링크다. 세 칸으로 이뤄진다.
  - 권한 명세서
  - 가짜 스타 신호
  - 관리 상태
- F3. 결과 위에 요약 한 문단(LLM)을 둔다.
- F4. 매일 급상승한 AI 도구 상위 20개를 미리 분석해 첫 화면에 보여 준다.
- F5. 모든 결과에 분석 시각, 커밋 SHA, "통과가 안전을 보장하지 않음" 문구, 이의 제기 링크를 표시한다.

### 뺀 것 (MVP 이후)

로그인, 설치한 도구의 버전 감시와 알림, 내 스택 맞춤 추천, 한국어 해설 전체, 저장소 비교.

## 4. 구조

```
웹 (Next.js, Vercel)
   │  분석 요청 / 진행 상황 SSE / 결과 조회
API 서버 (Spring Boot 3.5, Java 17. 가상 스레드가 필요해지면 21로)
   │                    │
PostgreSQL           Redis
 저장소, 분석 작업,      IP별 요청 제한,
 결과, 스타 표본         결과 캐시
   │
분석 워커 (API 서버 안, 작업 대기열에서 꺼내 처리)
   │
GitHub API(REST 압축 파일, GraphQL 스타 표본) / Scorecard API / LLM API
```

### 결정과 이유

| 결정 | 이유 |
|---|---|
| 작업 대기열은 PostgreSQL(`SELECT … FOR UPDATE SKIP LOCKED`) | 처음엔 저장소를 하나라도 줄인다. 워커를 여러 대로 늘려야 할 때 별도 대기열로 바꾼다. |
| 결과 키는 `(저장소, 커밋 SHA)` | 같은 커밋의 결과는 바뀌지 않는다. 다시 요청하면 저장된 결과를 바로 돌려준다. |
| 같은 커밋 동시 요청은 작업 하나 | `analysis_job`에 `(repo_id, commit_sha)` 유니크 제약. 두 번째 요청은 기존 작업을 구독한다. |
| 저장소를 실행하지 않음 | 정적 분석만 한다. 그래서 격리 실행 환경이 필요 없다. |
| 분석기는 서로 독립 | 하나가 실패해도 나머지 칸은 보여 준다. 분석기마다 결과 행을 따로 저장한다. |

## 5. 데이터 모델(초안)

| 테이블 | 핵심 열 | 비고 |
|---|---|---|
| `repository` | id, owner, name, stars, default_branch, last_seen_at | `(owner, name)` 유니크 |
| `analysis_job` | id, repo_id, commit_sha, status, requested_by_ip_hash, attempts, next_run_at, created_at | `(repo_id, commit_sha)` 유니크. status: QUEUED → RUNNING → DONE / PARTIAL / FAILED |
| `analyzer_result` | job_id, analyzer(PERMISSION/STARS/MAINTENANCE/SUMMARY), status, payload(jsonb), error, finished_at | `(job_id, analyzer)` 기본키 |
| `finding` | id, job_id, category, severity_hint, file_path, line, snippet, rule_id | 권한 명세서의 근거 한 줄씩 |
| `stargazer_sample` | repo_id, sampled_at, login, starred_at, account_created_at, followers, public_repos, active_flag | 가짜 스타 계산 근거 |
| `daily_pick` | picked_on, rank, repo_id, star_delta | 첫 화면 상위 20 |

## 6. 분석기

### 6-1. 권한 명세서

1. **받기:** GitHub REST로 해당 커밋의 압축 파일(tarball)을 받는다.
   - 크기 상한 50MB, 파일 수 상한 5,000개. 넘으면 앞부분만 분석하고 결과에 "일부만 분석" 표시.
   - 압축을 풀 때 압축 폭탄(풀린 크기/압축 크기 비율 상한), `../` 경로 탈출, 심볼릭 링크를 막는다.
   - 디스크에 풀지 않고 스트림으로 읽는 방식을 먼저 검토한다.
2. **종류 판별:**

| 신호 | 종류 |
|---|---|
| `SKILL.md` | skill |
| `hooks.json` 또는 설정 파일의 `hooks` 항목 | hook |
| `@modelcontextprotocol/sdk`, `mcp` 의존성 | MCP 서버 |
| `.claude-plugin/plugin.json` | 플러그인 |
| 해당 없음 | 일반 저장소(같은 규칙으로 검사) |

3. **규칙 탐지(1차):**

| 범주 | 예시 규칙 |
|---|---|
| 셸 실행 | `child_process`, `subprocess`, `os.system`, `Runtime.exec`, skill의 `allowed-tools`에 Bash |
| 파일 접근 | `~/.ssh`, `~/.aws`, 홈 폴더 경로, 쓰기 모드 파일 열기 |
| 외부 전송 | `fetch`, `axios`, `requests`, `curl` 대상 URL → 도메인 목록 추출 |
| 환경 변수, 비밀 | `process.env`, `os.environ`, `.env` 읽기 |
| 설치 스크립트 | `postinstall`, `preinstall`, `curl … | bash` |
| 난독화 | 긴 base64 문자열, `eval`, 동적 `Function` |

4. **LLM 판정(2차):** 마크다운 파일(SKILL.md, 도구 설명)에서 프롬프트 인젝션 의심 문구를 판정한다. 입력은 md 파일과 규칙이 찾은 줄 주변으로만 줄인다.
5. **출력:** 범주별 표. 각 항목에 파일, 줄 번호, 해당 줄, 규칙 id.

### 6-2. 가짜 스타 신호

- GraphQL `stargazers(orderBy: {field: STARRED_AT, direction: DESC})`로 최근 300개 표본을 가져온다(스타 시각과 계정 정보 포함).
- 판별 기준은 StarScout의 두 가지를 따른다.
  - **저활동 계정:** 생성 직후이고, 팔로워와 공개 저장소가 거의 없고, 활동이 없는 계정.
  - **같은 시각 몰림:** 짧은 시간 창에 비슷한 성격의 계정이 몰려 스타를 누른 묶음.
- 출력: 표본 중 저활동 계정 비율, 몰림 묶음 수와 시각, 표본 크기. "판정"이 아니라 "신호"로 표시한다.
- 같은 저장소는 하루 한 번만 표본을 다시 뽑는다.

### 6-3. 관리 상태

- GitHub API: 마지막 커밋 시각, 최근 90일 커밋 수, 기여자 수, 이슈 첫 응답 시간 중앙값(최근 이슈 30개 표본).
- Scorecard API(`api.scorecard.dev`): 결과가 있으면 "Maintained" 등 관련 검사만 가져온다. 없으면 "Scorecard 결과 없음"으로 표시.

### 6-4. 요약

- 세 분석기 결과(LLM이 아닌 구조화된 값)만 입력으로 한 문단을 만든다. 코드 원문은 넣지 않는다.

## 7. 외부 호출 규칙

| 대상 | 시간 제한 | 동시 상한 | 실패 시 |
|---|---|---|---|
| GitHub REST(압축 파일) | 연결 3초, 전체 60초 | 4 | 5xx·시간 초과는 지수 백오프로 최대 3회 |
| GitHub GraphQL | 10초 | 4 | 한도 초과(403/429)는 응답의 재설정 시각까지 작업을 미룸(`next_run_at`) |
| Scorecard API | 5초 | 4 | 실패하면 그 칸만 "가져오지 못함" |
| LLM API | 30초 | 2 | 실패하면 규칙 결과만으로 PARTIAL, 나중에 요약만 다시 시도 |

- 위 숫자는 첫 값이다. k6와 실제 응답 시간을 재서 다시 정한다.

## 8. 비용과 한도

### GitHub API

- 로그인한 REST 요청은 시간당 5,000회다. 검색 API는 따로 한도가 있으며, 실제 값은 `/rate_limit` 응답으로 확인한다.
- GraphQL은 별도의 점수 한도가 있다. 스타 300개 표본 한 번의 비용은 **아직 재지 않았다.** 첫 구현에서 쿼리에 `rateLimit { cost remaining }`을 넣어 실제 비용을 재고, 하루 분석 상한을 거기서 계산한다.
- 한도를 넘으면 사용자 요청보다 F4(일일 상위 20) 작업을 먼저 미룬다.

### LLM

- 분석 한 건의 입력 토큰 상한과 하루 전체 비용 상한을 설정값으로 둔다. 상한에 닿으면 LLM 단계만 건너뛰고 PARTIAL로 낸다.
- 구체적인 모델과 금액은 구현 직전에 최신 요금표로 정한다.

## 9. 오류 처리

| 상황 | 처리 |
|---|---|
| 비공개 저장소, 없는 저장소 | 요청 시점에 바로 400/404 안내. 작업을 만들지 않음 |
| 너무 큰 저장소 | 상한까지 분석하고 "일부만 분석" 표시 |
| GitHub 한도 초과 | 작업을 미루고 예상 대기 시간을 SSE로 알림 |
| LLM 실패, 비용 상한 | 규칙 결과로 PARTIAL. 요약 칸만 "다시 시도" |
| 분석기 하나 실패 | 나머지 칸은 보여 주고, 실패한 칸만 FAILED |
| 워커가 작업 도중 죽음 | `RUNNING`이 오래된 작업을 되돌려 다시 잡음(`attempts` 상한 3) |
| 같은 IP의 요청 폭주 | Redis로 IP별 분석 요청 제한(429). 결과 조회는 제한하지 않음 |

## 10. 신뢰와 분쟁 대비

- "위험", "악성" 같은 단정어를 쓰지 않는다. "발견된 신호"와 근거 줄로만 보여 준다.
- 모든 결과에 분석 시각, 커밋 SHA, "통과가 안전을 보장하지 않음"을 표시한다.
- 저장소 주인용 이의 제기 링크를 둔다(MVP는 이메일 양식).
- 다른 도구의 탐지 규칙을 가져올 때는 각 라이선스를 먼저 확인한다. 맞지 않으면 아이디어만 참고하고 직접 구현한다.

## 11. 테스트

- **시험용 저장소 묶음(fixtures):** 셸 실행, 외부 전송, 인젝션 문구, `postinstall`, 압축 폭탄, 경로 탈출, 심볼릭 링크를 일부러 넣은 작은 저장소들. 규칙마다 "찾아야 할 것"과 "찾으면 안 되는 것"을 둔다.
- **외부 API:** WireMock으로 GitHub, Scorecard, LLM을 대신하고 한도 초과, 시간 초과, 5xx를 재현한다.
- **DB:** Testcontainers PostgreSQL. 같은 커밋 동시 요청 10건이 작업 1개로 끝나는지, 죽은 워커의 작업이 다시 잡히는지 확인한다.
- **불변식:**
  - 한 `(repo_id, commit_sha)`에 작업은 하나.
  - 작업은 DONE·PARTIAL·FAILED 중 하나로 끝난다.
  - 결과의 모든 finding은 실제로 존재하는 파일과 줄을 가리킨다.

## 12. 트래픽 가정(임시)

| 항목 | 가정 |
|---|---|
| 분석 요청 | 평소 하루 수백 건 |
| 결과 페이지 조회 | 평소 하루 수천 건 |
| 몰림 | 커뮤니티에 결과 링크가 퍼질 때 한 페이지에 1시간 동안 평소의 50배 |

- 출시 전에 근거(커뮤니티 규모, 비슷한 서비스 공개 수치)를 찾아 다시 정한다.
- 결과 페이지는 커밋 SHA로 고정되므로 캐시하기 쉽다. 몰림 대비의 첫 수단이다.

## 15. 구현에서 달라진 점(계획 1)

- 풀린 크기는 비율 대신 200MB 절대 상한으로 막는다.
- 크기 초과나 바이너리로 건너뛴 파일 수를 결과에 표시한다(`skippedFiles`). 크기 초과로 건너뛰면 "일부만 분석"으로 표시한다.
- 링크 항목은 분석에서 제외한다.
- 파이썬 MCP 판별은 의존성 선언 위치로 한정한다.
- `curl | sh` 정규식은 길이 상한을 두고, 근거 줄은 걸린 위치 중심으로 잘라 보여준다.
- GitHub 리다이렉트는 수동으로 따라가고, 다른 호스트로는 토큰을 보내지 않는다.
- GitHub 보조 한도(secondary rate limit)도 한도 초과로 처리한다.
- 작업 시도 횟수로 펜싱해, 다른 워커가 이어받은 작업의 결과는 버린다.
- 스케줄러 풀은 2개, 본문 읽기 기한은 120초다.
- 재시도 간격은 설계의 지수 증가 대신 30초 x 시도 횟수의 선형 증가다.
- 요청 시점에 GitHub 한도가 초과되면 503과 Retry-After로 답한다.
- 오류 응답은 모두 ApiResponse로 감싼다.
- 도메인 목록은 200개까지만 담고, 넘으면 `domainsTruncated`로 표시한다.
- 실패(FAILED)한 커밋을 30분이 지난 뒤 다시 요청하면 대기열에 다시 넣는다. 시도 횟수(펜싱 값)는 되돌리지 않고 `attempt_base`로 회차를 나눠, 시도 상한 3회는 회차마다 다시 센다.

## 16. 구현에서 달라진 점(계획 2)

- 파일마다 종류(코드, 에이전트 지시문, 설정, 문서)와 위치(본 위치, 테스트·예제·문서 폴더)를 정하고, 코드 문법 규칙(eval, fetch, process.env 등)은 코드 파일에만 건다. `src/main` 아래 폴더 이름은 패키지 이름이라 위치 판단에 쓰지 않는다.
- 근거는 지우지 않고 주요와 참고로 나눈다. 테스트·예제·문서 폴더와 `.github`의 근거는 참고다. 문서의 설치 명령(curl | bash)은 본 위치면 주요다.
- 도메인 목록은 본 위치의 코드·지시문·설정에서만 모은다.
- 결과에 범주별 주요 근거 수(`primaryCounts`)와 참고 근거 수(`secondaryFindings`)를 담는다. 근거 상한 500개는 본 위치 파일부터 채운다.
- SKILL.md의 `allowed-tools`는 앞머리에서만, 한 줄 표기와 목록 표기를 모두 본다.
- `| sudo bash`, `bash <(curl …)`, `sh -c "$(curl …)"`도 설치 명령으로 찾는다.
- MCP 서버 판별은 package.json 의존성 필드, 파이썬 개발 의존성(dependency-groups, uv, poetry), requirements 변형 파일, fastmcp까지 넓혔다.
- FIFO·장치 항목은 읽지 않고, 서브모듈은 분석하지 않은 부분으로 알린다(`submodules`).
- 빈 저장소는 요청 시점에 409로 답한다.
- GitHub 리다이렉트는 http/https만, https에서 http로는 따라가지 않는다.
- 주요/참고 구분은 경로 이름만 본다. 코드를 테스트·예제 폴더에 두면 참고로 내려가므로, 참고 근거도 결과에서 지우지 않고 모두 보여 준다.

## 17. 구현에서 달라진 점(계획 3)

- 압축 파일 본문은 무응답 기한(30초)과 전체 기한(300초)으로 감시한다. 느리지만 계속 오는 큰 저장소는 끝까지 받고, 막힌 응답과 끝없이 찔끔 오는 응답은 끊는다.
- 재시도 시각은 실패한 때를 기준으로 잡는다.
- 작업 실행 시각은 DB 시계 대신 앱 시각으로 정한다.
- GitHub 호출은 동시에 8개까지 나간다. 2초 안에 자리가 나지 않으면 한도 초과와 같은 길(워커는 미루기, API는 503 + Retry-After)로 보낸다.
- 분석 요청은 같은 IP에서 1분에 10번까지다. Redis 고정 창으로 세고, 넘으면 429 + Retry-After. 결과 조회는 제한하지 않는다. Redis에 닿지 못하면 제한 없이 통과시킨다(요청마다 최대 0.5초 지연과 경고 로그).
- 클라이언트 IP는 앞단 프록시(사설 대역)가 준 `X-Forwarded-For`만 믿는다. 배포 때 프록시 주소가 사설 대역이 아니면 `server.tomcat.remoteip.internal-proxies`를 맞춰야 한다.
- 이미지 data URI(png, jpeg, gif, webp)와 노트북 출력 이미지는 base64 난독화 근거에서 뺀다. 스크립트를 담을 수 있는 svg는 그대로 본다. `eval "$(curl …)"`, `source <(curl …)`, `| sudo -u root bash`도 설치 명령으로 찾는다.
- 로컬 Redis는 `127.0.0.1:6381`에 띄운다.

## 18. 구현에서 달라진 점(계획 4)

- 결과에 분석 시각(`analyzedAt`), 고정 안내 문구(`notice`), 이의 제기 창구(`disputeUrl`, 설정값)를 붙인다.
- 405는 `Allow`, 415는 `Accept` 헤더로 고칠 방법을 알린다. 잘못된 설정값이면 앱이 뜨지 않는다.
- 배포는 서버 한 대의 docker compose(app, PostgreSQL, Redis, Caddy)다. 외부에는 Caddy의 80/443만 열고, 상태 확인(`/actuator/health`)은 컨테이너 안에서만 쓴다. 백업은 저장소 밖에 하루 한 번 남긴다. 절차는 `docs/02-배포.md`.
- 클라이언트 IP는 Caddy가 실제 접속 IP로 채운다. 요청에 `X-Forwarded-For`를 넣어도 요청 제한 키가 바뀌지 않는 것을 로컬에서 확인했다.
- CI는 GitHub Actions에서 `./run_tests.sh`를 돌린다.

## 19. 구현에서 달라진 점(계획 5)

- 웹은 같은 저장소의 `web/` 폴더에 둔다(Next.js). 화면이 입력 하나와 결과 하나라 UI·상태 관리 라이브러리는 넣지 않았다.
- 분석 요청과 SSE 는 브라우저가 API 를 직접 부른다(CORS). 웹 서버를 거치면 IP 별 요청 제한이 웹 서버 IP 하나로 묶인다. 결과 페이지 첫 조회만 웹 서버가 부른다.
- SSE 는 구독마다 DB 를 부르지 않고, 1초마다 구독 중인 작업 전체의 상태를 쿼리 한 번으로 읽어 바뀐 것만 보낸다. 끝난 상태를 보내면 닫는다. 동시 구독 상한 500, 넘으면 503 이고 화면은 폴링으로 바꾼다.
- 9절의 "예상 대기 시간을 SSE 로 알림"은 아직 하지 않았다. 지금은 상태만 보낸다.
- 서비스 이름은 가칭 "까보기"다(14절).
