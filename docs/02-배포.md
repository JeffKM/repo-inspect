# 배포

서버 한 대(설계 13절)에 docker compose 로 app, PostgreSQL, Redis, Caddy 를 띄운다. 외부에는 Caddy 의 80/443 만 연다.

## 준비

- 서버: 시드니 리전 EC2, 메모리 2GB 이상(t3.small 이상). 압축을 푼 텍스트가 최대 200MB 까지 메모리에 올라오고, app 컨테이너 상한은 1.5GB 다.
- 보안 그룹: 22(관리자 IP 만), 80, 443. 5432·6379·8080 은 열지 않는다.
- 서버에 Docker 와 compose 플러그인을 설치한다.
- 도메인의 A 레코드를 서버 공인 IP 로 잡는다. Caddy 가 HTTPS 인증서를 자동으로 받는다.

## 비밀값

서버의 저장소 폴더에 `.env` 를 만든다. 이 파일은 커밋하지 않는다(`.gitignore` 에 있음). 권한은 `chmod 600 .env`.

| 키 | 설명 |
|---|---|
| `DB_PASSWORD` | PostgreSQL 비밀번호(임의의 긴 값) |
| `REDIS_PASSWORD` | Redis 비밀번호(임의의 긴 값) |
| `GITHUB_TOKEN` | 공개 저장소 읽기만 되는 GitHub 토큰(권한 없는 fine-grained 토큰) |
| `SITE_ADDRESS` | 서비스 도메인(예: `inspect.example.com`) |
| `DISPUTE_URL` | 이의 제기 창구 주소(선택) |

## 올리기

```bash
git pull
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml ps        # app 이 healthy 인지
curl -s https://<도메인>/api/analyses/1              # 404 JSON 이면 연결은 정상
```

## 백업

PostgreSQL 은 하루 한 번 덤프를 남긴다(cron 예시).

```bash
docker compose -f docker-compose.prod.yml exec -T postgres pg_dump -U repoinspect repoinspect | gzip > backup/$(date +%F).sql.gz
```

## 배포 때 확인할 것

계획 3 최종 리뷰에서 나온 항목이다.

1. **클라이언트 IP:** 앞단이 이 compose 의 Caddy 라면 IP 제한이 접속자별로 잡힌다. Cloudflare 나 공인 IP 로드밸런서를 앞에 더 두면 모든 요청이 그 IP 하나로 묶이므로 `server.tomcat.remoteip.internal-proxies` 를 맞춘다. 배포 뒤 서로 다른 두 IP 에서 요청해 따로 세는지 확인한다.
2. **Redis 장애:** 요청 제한이 풀리고 요청마다 최대 0.5초가 붙는다. app 로그의 "요청 제한 저장소에 닿지 못해" 경고를 지켜본다.
3. **GitHub 한도:** 분석 요청 1건에 GitHub 호출 2회 + 압축 파일 1회다. 토큰 한도(시간당 5,000회)의 남은 양을 지켜본다.
4. **서버를 늘릴 때:** GitHub 동시 호출 상한(8)은 서버마다 따로 걸리므로 대수에 맞춰 낮춘다. 작업 시각을 앱 시계로 정하므로 서버 시계를 NTP 로 맞춘다.
5. **기한:** 본문 전체 기한(300초)과 헤더 대기, 스캔 시간을 합친 값이 멈춘 작업 복구 기준(10분)보다 짧아야 한다. `read-deadline-seconds` 를 늘리면 복구 기준도 같이 본다.
6. **메모리:** 워커는 한 번에 한 작업만 한다는 전제로 app 메모리를 1.5GB 로 잡았다. 워커를 늘리면 메모리도 다시 계산한다.
