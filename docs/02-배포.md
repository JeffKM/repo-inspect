# 배포

서버 한 대(설계 13절)에 docker compose 로 app, PostgreSQL, Redis, Caddy 를 띄운다. 외부에는 Caddy 의 80/443 만 연다.

## 준비

- 서버: 시드니 리전 EC2, 메모리 2GB 이상(t3.small 이상). 압축을 푼 텍스트가 최대 200MB 까지 메모리에 올라오고, app 컨테이너 상한은 1.5GB 다.
- 보안 그룹: 22(관리자 IP 만), 80, 443. 5432·6379·8080 은 열지 않는다.
- 서버에 Docker 와 compose 플러그인을 설치한다.
- 도메인의 A 레코드를 서버 공인 IP 로 잡는다. Caddy 가 HTTPS 인증서를 자동으로 받는다.

## 비밀값

서버의 저장소 폴더에 `.env` 를 만든다. 이 파일은 커밋하지 않는다(`.gitignore` 에 있음). 권한은 `chmod 600 .env`.

| 키 | 설명 |
|---|---|
| `DB_PASSWORD` | PostgreSQL 비밀번호(임의의 긴 값) |
| `REDIS_PASSWORD` | Redis 비밀번호(임의의 긴 값) |
| `GITHUB_TOKEN` | 공개 저장소 읽기만 되는 GitHub 토큰(권한 없는 fine-grained 토큰) |
| `SITE_ADDRESS` | 서비스 도메인(예: `inspect.example.com`) |
| `DISPUTE_URL` | 이의 제기 창구 주소(선택) |
| `WEB_ORIGINS` | 웹 화면 주소(예: `https://web.example.com`). 쉼표로 여럿. 비우면 브라우저에서 API 를 부를 수 없다 |

## 올리기

```bash
git pull
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml ps        # app 이 healthy 인지
curl -s https://<도메인>/api/analyses/1              # 404 JSON 이면 연결은 정상
```

## 웹 화면(Vercel)

1. Vercel 에서 이 GitHub 저장소로 새 프로젝트를 만든다. Root Directory 는 `web`.
2. 환경 변수 `NEXT_PUBLIC_API_BASE` 에 API 주소(예: `https://api.example.com`)를 넣고 배포한다.
3. 서버 `.env` 의 `WEB_ORIGINS` 에 Vercel 이 준 주소(또는 웹 도메인)를 넣고 `docker compose -f docker-compose.prod.yml up -d` 로 app 을 다시 띄운다.
4. 웹에서 분석을 요청해 진행 상태가 바뀌다가 결과가 나오는지 본다.

- 분석 요청과 진행 상태(SSE)는 브라우저가 API 를 직접 부른다. Vercel 서버를 거치면 IP 별 요청 제한이 Vercel IP 하나로 묶이기 때문이다.
- 결과 페이지 첫 조회는 Vercel 서버가 API 를 부른다. 조회는 요청 제한이 없다.
- Caddy 는 `text/event-stream` 응답을 바로바로 흘려보내므로 SSE 를 위해 따로 설정할 것이 없다.
- `WEB_ORIGINS` 에는 운영 웹 주소만 넣는다. Vercel 미리 보기 배포 주소는 배포마다 바뀌므로 CORS 에 막힌다.

## 백업

PostgreSQL 은 하루 한 번 `deploy/backup.sh` 로 덤프를 남긴다. 백업은 저장소 밖(기본 `/var/backups/repo-inspect`)에 쌓이고 14일이 지나면 지워진다. 덤프가 실패하면 파일을 남기지 않고 실패로 끝난다.

```bash
sudo mkdir -p /var/backups/repo-inspect && sudo chown "$USER" /var/backups/repo-inspect
crontab -e
# 매일 03:30 (경로는 서버의 저장소 위치로)
30 3 * * * /home/ec2-user/repo-inspect/deploy/backup.sh >> /var/backups/repo-inspect/backup.log 2>&1
```

백업 파일은 서버 디스크에만 있으므로, 서버를 잃어도 남기려면 S3 같은 다른 저장소로 옮긴다.

복원은 app 을 멈추고 덤프를 그대로 흘려 넣는다. 덤프에 `--clean` 이 들어 있어 기존 테이블을 지우고 다시 만든다.

```bash
docker compose -f docker-compose.prod.yml stop app
gunzip -c /var/backups/repo-inspect/<날짜>.sql.gz | docker compose -f docker-compose.prod.yml exec -T postgres psql -U repoinspect -d repoinspect
docker compose -f docker-compose.prod.yml start app
```

cron 이 `docker` 를 찾는지는 처음 한 번 `deploy/backup.sh` 를 직접 돌리고 `/var/backups/repo-inspect` 에 파일이 생기는지로 확인한다.

## 배포 때 확인할 것

계획 3 최종 리뷰에서 나온 항목이다.

1. **클라이언트 IP:** 앞단이 이 compose 의 Caddy 라면 IP 제한이 접속자별로 잡힌다. Cloudflare 나 공인 IP 로드밸런서를 앞에 더 두면 모든 요청이 그 IP 하나로 묶이므로 `server.tomcat.remoteip.internal-proxies` 를 맞춘다. 배포 뒤 서로 다른 두 IP 에서 요청해 따로 세는지 확인한다.
2. **Redis 장애:** 요청 제한이 풀리고 요청마다 최대 0.5초가 붙는다. app 로그의 "요청 제한 저장소에 닿지 못해" 경고를 지켜본다.
3. **GitHub 한도:** 분석 요청 1건에 GitHub 호출 2회 + 압축 파일 1회다. 토큰 한도(시간당 5,000회)의 남은 양을 지켜본다.
4. **서버를 늘릴 때:** GitHub 동시 호출 상한(8)은 서버마다 따로 걸리므로 대수에 맞춰 낮춘다. 작업 시각을 앱 시계로 정하므로 서버 시계를 NTP 로 맞춘다.
5. **기한:** 본문 전체 기한(300초)과 헤더 대기, 스캔 시간을 합친 값이 멈춘 작업 복구 기준(10분)보다 짧아야 한다. `read-deadline-seconds` 를 늘리면 복구 기준도 같이 본다.
6. **메모리:** 워커는 한 번에 한 작업만 한다는 전제로 app 메모리를 1.5GB 로 잡았다. 워커를 늘리면 메모리도 다시 계산한다.
7. **SSE:** 동시에 열린 진행 상태 스트림 상한은 500(`repo-inspect.events.max-subscribers`)이다. 넘으면 503 이고 화면은 3초 폴링으로 바꾼다. 상태는 1초마다 구독 중인 작업 전체를 쿼리 한 번으로 읽는다.
